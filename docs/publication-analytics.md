# Publication results

Pubrick shows a brand's last 100 published posts for a selected 7, 30 or 90 day window at **Brands → Results**. The count and totals on this screen describe only those displayed posts. Unknown counters are excluded; a measured zero is shown as `0`. Deleted channels and their detached receipts cannot be attributed to a current brand, so they remain in the delivery history but are absent from brand results.

The activity overview on this screen has an **AI call history** detail section. Opening it reads the last 50 persisted `usage_ledger` calls attributable to the brand across all time, ordered by call record time and then ID. Each row shows the step, provider, model, time and cost source. Provider-reported figures and local price-table estimates are distinguished; unpriced or possibly billed calls show unknown cost, while a refused call with no tokens shows no recorded charge. Run and draft links are emitted only when their surviving rows belong to the requested brand. Calls with no surviving run, item or channel brand link are omitted after deletion; calls that never reached the ledger cannot appear. This history does not reconstruct provider invoices or audience reach. `GET /api/analytics/brands/:brandId/spend-history` is read-only, organization- and brand-scoped, capped at 50 rows, and returns no prompt text or credentials.

VK posts with a valid stored post ID and a connected channel can be checked with **Check metrics**. Pubrick calls VK `wall.getById` using the existing encrypted channel credentials, validates the returned community and post ID, then records available view, like, comment and repost counters. A post can be checked once per 15 minutes. The latest observation is marked as potentially outdated after 24 hours. Provider errors, missing posts and absent counters remain explicit unavailable or error states. No metric read is made during a normal page load.

**Automatic VK metrics** can be enabled for each VK channel under its brand's channel settings. It is off by default. The worker scans once per hour, considers only published posts from the last 90 days with a live channel and a stored VK post ID, and queues at most five pages of 100 posts per scan. An available observation becomes due after 24 hours; unavailable and error observations after one hour. Each job rechecks the channel opt-in, organization, brand and publication before accessing its encrypted credentials. Its payload contains only identifiers. The channel queue serializes reads and deduplicates each publication for an hour; the database's conditional 15-minute claim is shared with **Check metrics** and is the final concurrency guard across API and worker replicas. A failed provider read records `error` with null counters. The screen shows only the latest observation; it does not infer a trend or historical series.

Telegram's legacy `cf_collect_metrics` task did not collect metrics; it only updated a timestamp. Pubrick does not repeat that behavior. Telegram, MAX, VC.ru and Dzen display **Not measured yet** with unknown values until a real platform-specific collector is implemented. The Results screen is read-only except for the VK check action. A successful check changes no publication status and does not trigger AI calls.

The API is org-scoped with `ActiveOrgGuard`: `GET /api/analytics/brands/:brandId?days=7|30|90` and `POST /api/analytics/brands/:brandId/publications/:publicationId/refresh`. The latter requires a published receipt linked to that brand and a VK channel; both the read and update select only explicit columns. The metric table stores one latest observation per receipt and carries `org_id` with a cascade to the organization. A conditional upsert claims the 15-minute window before any provider request, including across API replicas.

VK method and object shape follow VK's published [API schema](https://github.com/VKCOM/vk-api-schema/tree/master/wall) and [official SDK method contract](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/Actions/Wall.php). Local tests use a fake HTTP server and make no provider requests.
