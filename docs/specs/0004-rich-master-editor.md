# Rich master editor

**Status:** design for a later aggregate release. The reference editor offered formatting and inline images. Pubrick already has approved inline image slots but keeps `content_items.body` as plain text for refinement offsets, provenance, channel adaptations, delivery and public API reads. This design brings supported formatting to the master editor without changing that canonical text contract.

## Document and projection

Use maintained TipTap packages for the browser editor and a strict JSON document as the saved rich representation. Start with paragraphs, H2/H3, bold, italic, ordered and unordered lists, and links. Keep the existing image-slot editor and alignment controls beside the text editor. Tables and image nodes need their own projection, tenancy and publication-snapshot design before release. Pasted HTML is parsed into the allowed document model; raw HTML nodes, arbitrary styles, external image nodes and unsupported marks are rejected. Link targets must use `https:`, `http:` or `mailto:`; strip tracking or dangerous attributes according to the existing URL policy. Bound document bytes, node count, nesting depth and link length on the server.

`body` remains normalized plain text. One shared, deterministic projection from validated rich JSON produces it. Define paragraph and heading line breaks, list markers and nesting, and whether visible link text carries its URL in text-only channels; show the exact projected text in the preview. Character offsets in refinement and provenance always refer to this projection, not ProseMirror positions. Before enabling the UI, golden tests must prove projected offsets, normalization and channel payloads. A rich document may be saved only when the supplied `body` equals its server-derived projection byte for byte after canonical normalization. Never derive plain text from unsanitized HTML in an API request.

## Storage and editing

Add nullable `rich_body jsonb` to `content_items` and `content_versions`, nullable rich snapshot data to `feed_entries`, and `body_revision integer NOT NULL DEFAULT 0` to `content_items`. Existing rows remain text only. Add strict typed DTOs in `packages/shared`. Content detail and full version responses include rich JSON and revision; queue list responses stay compact. `PATCH /api/content/:id` accepts `{ body, richBody, expectedBody, expectedBodyRevision }`. Under the existing item lock, check both expectations, validate JSON and projection, and write both forms plus incremented revision atomically. A formatting-only save adds a complete human version even when `body` does not change; it does **not** mark unchanged AI-authored sentences as human-edited or waive the approval gate. Restoring a rich version restores both forms and adds a new version; restoring a text-only version clears rich JSON. A stale save returns 409 with current revision so the editor can preserve the user's unsaved work.

Every current plain-text writer that changes `body` must clear `rich_body` in the same transaction unless it explicitly rebases a validated rich document. This includes accepted refinement, AI draft revision, version restore, and older body-only API clients. A body-only no-op preserves rich formatting. The editor explains a formatting reset after another text operation; prior rich versions remain in history. Channel variants and publisher workers continue to consume the projected `body`. Keep all existing approval, claim-review, selection-refinement, image-slot and provenance controls active during rich editing.

## Rendering and immutable output

Render validated JSON to HTML on the server using a maintained TipTap HTML renderer, then sanitize the result with an explicit element/attribute allowlist before article display, VC.ru package export or public RSS snapshot creation. Render links safely (`rel` and target policy); disallow scripts, events, inline styles, arbitrary `img` URLs and iframe content. A malformed stored document falls back to escaped plain text and is observable as an internal error, never returned as raw HTML. The published RSS entry stores a snapshot of the rich document or final sanitized HTML, so later master edits cannot alter an existing feed item. Existing `feed_entry_images` and `content_image_slots` remain the only image sources in this first phase, with their present ownership and immutable media snapshots.

The formatting UI belongs inside the current draft editor. Use selection controls and a keyboard link shortcut rather than a permanent ribbon; retain the stationary Refine action, calm typography, primary action hierarchy and focus/error patterns in `docs/ux-patterns.md`. Show the channel text preview alongside the formatted article preview so editors can see what Telegram, VK and other plain-text outputs will actually send. Hide rich controls until the API advertises support, because an older API might ignore a new JSON field. Deploy additive schema/API support before UI.

## Acceptance

Tests cover projection and Unicode offsets; paragraph/list/link text in each channel; rejected unsupported nodes and URL schemes; escaped XSS payloads in editor, article, VC package and RSS; 409 stale saves; formatting-only history without false human authorship; refinement acceptance and AI revision clearing stale formatting; rich and text-only version restore; old-client body updates; existing image-slot paragraph positions; and immutable feed snapshots. Run focused checks while building, then one aggregate review and the full local quality suite with the release candidate.
