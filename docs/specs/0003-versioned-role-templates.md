# Versioned role templates

**Status:** design for review. This adds the remaining active legacy capability: a manager can edit, preview, activate, and restore the role instruction body used by generation. It does not import the legacy global `cf_prompt_templates` table, Jinja2 interpreter, mutable rows, automatic prompt selection, or performance score.

## Starting point and boundary

Pubrick already has immutable **additional guidance** revisions in `prompt_revisions`, shown in Settings → Generation guidance. The greatest guidance version is active, and `pipeline_runs.guidance_snapshot` pins its exact text at the first successful worker claim. Guidance usage, review decisions, and brand outcome reports are observational. This feature keeps those contracts and names the new object **role template** throughout the API and UI so a guidance revision can never be mistaken for a template revision.

The five roles are `researcher`, `writer`, `editor`, `factcheck` (labelled “Claims to verify”), and `adapter`. A template replaces only the editable role prose now interleaved with `spec.role` in `packages/ai/src/steps`; it does not replace `defineStep`, `instructionsFor`, `materialFor`, `contentTypePolicy`, the step's Zod schema, model-call options, or the worker's fencing, metering, and checkpoints. The adapter has one organization-wide role template rendered for each selected channel, not an independently active template per channel. Existing guidance is appended after the selected template as today. Protected role rules and content-type policy are emitted outside the editable body, after it, with explicit precedence over it. The code-owned wrapper retains the date, brand configuration, untrusted-material warning, JSON-only instruction, and channel identity/limit rules. A template may add editorial direction but cannot remove those rules by omission.

The extraction must use an explicit role inventory, not a broad “editable prompt” replacement:

| Role | Editable default body | Immutable code-owned rules and output contract |
| --- | --- | --- |
| Researcher | Planning angle, ordered points, and avoid-list style | No web access or claimed verification; no invented facts; `researchSchema` requires angle/key points and retains `avoid`. |
| Writer | Draft voice, structure, and style | No unsupported additions or long copied passages; material remains fenced; `draftSchema` and `MAX_BODY_LENGTH` bound the body. |
| Editor | Clarity, tone, and concise changes summary | No new claims; edited-body bound; `editSchema` owns `body`, `changes`, and optional advisory score. |
| Factcheck | How to phrase the claim list for human review | The step verifies nothing; source excerpts are unverified; code validates quote/source pairs; `factcheckSchema` and the shared “Claims to verify” label stay fixed. |
| Adapter | Channel-specific editorial phrasing | Channel identity and platform limit, no added claims, no mechanical truncation, shared adaptation schema and repair classification remain fixed. |

Keep each default role's complete current instruction bytes as a baseline fixture before extraction. With the same date, brand, content type, channel, and guidance, selecting built-in must produce byte-identical `instructions` to the pre-feature implementation for all five roles, every content type, and every supported adapter platform. The extraction may rearrange code ownership internally but may not silently change the default prompt. New protected text that cannot meet this parity is a separate reviewed product change.

This is a prompt boundary, not a claim that a model always obeys the higher-priority prose. Validation checks syntax and size; it cannot prove the semantic safety or quality of manager-written instructions. The structured-output schema, length checks, source-quote validation, provenance calculations, human involvement gate, and human publication approval remain executable server rules. In particular, “Claims to verify” never becomes verified claims, supplied source text never becomes independent evidence, and no UI copy claims originality.

## Data and authorization

Add `role_template_revisions`: `id` UUID, `org_id` non-null FK, closed `role`, positive `version`, `source` text, `source_sha256`, `created_by` nullable user FK, and `created_at`. Unique `(org_id, role, version)` and `(org_id, role, id)`; source and its hash are immutable after insert. Add `role_template_heads`: one row per `(org_id, role)`, `active_revision_id` nullable, and nonnegative `generation` used for compare-and-swap. The nullable composite FK `(org_id, role, active_revision_id) → role_template_revisions(org_id, role, id)` makes a cross-tenant or cross-role pointer impossible at the database boundary. An absent head means built-in source with generation `0`; the first save or activation lazily creates that role's head under an organization-row lock. This covers organizations created through Better Auth without relying on an undocumented creation hook or trigger; migration need not seed existing or future organizations. `NULL` active ID means built-in source. Do not model activation by mutating `is_active` flags on revisions. Do not delete revisions while their organization exists; run snapshots and decision history remain intelligible after rollback. Both tables are organization scoped, and every repository method takes `orgId` first and uses explicit selected columns.

The existing guidance table, its implicit latest-version behavior, and its endpoints remain distinct. Template source is never stored in guidance. The API uses `ActiveOrgGuard` and the existing manager brand scope (`owner`/`admin`) for **every** template list, history, preview, create, activate, usage, and outcomes request. A foreign revision ID returns 404 for the active organization or role. No cross-tenant template text, count, preview, or existence hint is returned. General members cannot read template source through these endpoints.

## Revision workflow and API

`GET /api/prompts/templates` returns the five roles with active revision metadata or `default`, head generation, and the built-in source for an authorized manager. `GET /api/prompts/:role/templates/revisions?cursor=<version>` returns 100 immutable revisions ordered by version descending and `nextCursor` from the last returned version; the next page uses `version < cursor`. `GET /api/prompts/:role/templates/revisions/:revisionId` retrieves any older revision by ID. Thus revision 101+ remains discoverable, previewable, and eligible for restoration. `POST /api/prompts/:role/templates/revisions` with `{source}` creates a draft and returns its ID/version. It does **not** activate it. Version allocation serializes on the organization row, as guidance creation does, and inserts once; identical text may still be a new auditable revision only when explicitly saved. Reject blank source, because built-in behavior is selected by activating `null`. Normalize CRLF to LF before length/hash validation; never silently trim meaningful spaces. Store the source exactly as normalized.

`POST /api/prompts/:role/templates/preview` takes `{source}` directly from the unsaved editor. It validates and renders entirely on the server using a fixed public sample fixture, returns rendered role-body text, referenced variable names, and size; it makes **no Gemini call**, consumes no BYOK key, writes no usage ledger row, and saves nothing. The response labels it a syntax/render preview, not an output sample or safety test. The same validator and renderer run before draft creation and at first claim. A resume verifies and uses stored instruction bytes without re-rendering under current code. A corrupted stored revision or snapshot causes a permanent pre-provider run failure with a closed error code rather than repeated paid retries.

`PUT /api/prompts/:role/templates/active` takes `{revisionId: uuid | null, expectedRevisionId: uuid | null, expectedGeneration: number}`. `revisionId: null` restores the built-in default. Under a transaction, lock the organization row `FOR UPDATE`, materialize the absent head if needed, then lock the head, compare **both** expected values, verify the target revision belongs to this organization and role, and atomically update the pointer and increment generation. Return 409 with the fresh head on a stale edit; never silently overwrite another manager's activation. A rollback is the same operation targeting an earlier revision. Re-activating the current target with a matching expectation is idempotent and does not increment generation. There is exactly one active choice per role; creating a draft never changes running or future generation until activation succeeds.

## Template language and bounded rendering

Use a deliberately small **one-pass variable substitution**, implemented as a fixed token scan in `packages/ai` rather than an interpreter dependency. The workspace has no templating dependency; Mustache and Handlebars would admit a broader language (sections/helpers/partials or escaping semantics) that this feature must reject. A scanner over the exact `{{name}}` token form and a closed variable map is shorter than configuring and then defending those languages. This is the narrow product-owned grammar, not a general parser. There are no conditionals, loops, filters, expressions, dot paths, includes, partials, environment access, helper registration, HTML escaping, or recursive expansion. A replacement value containing `{{...}}` stays literal; never pass it through a second render.

Allow only `{{current_date_utc}}` (ISO date), `{{content_type}}` (validated run enum), and `{{content_language}}` (validated language code) for all roles. The adapter alone also permits `{{channel_platform}}` (closed platform enum) and `{{channel_limit}}` (integer from the shared platform limit). Do not expose brand voice/name, channel name, credentials, user brief, pasted source, knowledge, news, previous model outputs, or arbitrary run JSON as variables. Brand and channel configuration that the current code already places in `instructions` stays in the code-owned wrapper, not in the variable map. No variable reads the process environment or database by name.

The preview fixture is constant and disclosed next to the preview: `2026-01-15`, `social_post`, `en`, brand name `Example Brand`, voice `Clear and practical`, audience `Readers`, empty guidance, and, for adapter, channel name `Example Telegram`, platform `telegram` with its actual shared limit. It contains no real tenant data. Runtime values come from a frozen, parsed claim receipt, including the UTC claim date and selected channel values. Unknown tokens, malformed braces, unsupported syntax, missing values, and NUL/control characters other than LF and tab are refused with a field error identifying a position and allowed variables. The JSON parser already decodes request bytes before Zod sees a string; do not promise to detect invalid raw UTF-8 at this layer. If the API accepts replacement characters from malformed raw bytes, that is an HTTP body-decoding policy outside this template validator. Literal braces must use a documented escape form (`\{{` and `\}}`); that escape is removed in one pass.

Bound normalized source to 12,000 Unicode code points and 48 KiB UTF-8, and rendered role body to 16,000 code points and 64 KiB. Preview and save validate those two limits using the disclosed fixture; save cannot certify the eventual full instruction size for every brand and channel. The preview returns both the rendered body and the sample **complete** instruction length, labelled as a sample. At claim, assemble every complete instruction string from the actual frozen receipt, selected source, guidance, wrapper, and content policy; refuse any string over 96 KiB UTF-8 **before** a provider call and mark the run with a closed permanent failure. A later resume reads stored instruction bytes and rechecks their bound. Bound the HTTP request body before JSON parsing. There is no recursion or expansion of rendered text.

## Run pinning and migration

Add nullable `pipeline_runs.template_snapshot` as an immutable object with a format/engine version and **exactly** the five role keys. `NULL` means never pinned. Each role entry is a discriminated `default` or `revision` selection; a revision has non-null ID and positive version, and a default has both null. Both carry exact normalized source and SHA-256. On claim and resume, recompute SHA-256 from source; for a revision, also compare ID/version/source hash to its same-org/role immutable row; for a default, compare source/hash to the retained built-in manifest for that engine version. Do not trust a self-consistent but invented default. The claim freezes a single typed receipt: parsed content type; UTC claim date; brand name, voice, audience, and content language; and each selected channel's ID, name, platform, and shared adapter limit. It also stores the **final rendered `instructions` bytes** and their hashes for researcher, writer, editor, factcheck, and each selected `adapter:<channelId>`, assembled from that source, pinned existing guidance, code-owned wrapper, and content policy. Thus a deploy changing the wrapper or policy cannot silently change a resumed run's instructions. No brief, pasted source, knowledge, news, prior model output, or rendered material block is stored in this snapshot. Template rendering, wrapper assembly, adapter schema/length checks, and adapter postprocessing must all consume this same receipt; no later `context()` read of mutable brand/channel configuration may supply one of those values. Live channel existence and authorization may still be checked before publication. A new engine that cannot execute a snapshot's schema/postprocessing version must fail closed or retain a compatible executor; it cannot reinterpret a checkpoint under changed rules.

At the first successful claim, write the complete snapshot in the **same fenced claim transaction** that changes the run to `running`, after validating selected channels and sizes. The generation step path accepts a validated instruction receipt and passes its stored string directly to `generateStructured`; it must not call today's `instructionsFor` again on resume. On lease takeover, queue redelivery, or checkpoint resume, keep the non-null snapshot unchanged and use its stored instruction strings for unfinished steps. A “Try again” action creates a new run and pins the then-current heads. A queued run claims after activation and uses the newly active source; a claimed run does not change when a manager activates, rolls back, or edits another revision.

Activation and first claim linearize on the organization row: both transactions lock it **first** (`FOR UPDATE` for activation, `FOR SHARE` for claim), before head or run rows. The claim then locks its run row, reads all five heads/revisions and brand/channel configuration in that transaction, builds the snapshot, and updates the run. Activation reads/writes one head only after its organization lock. A claim observes either all activations committed before its organization lock or none that wait behind it; it cannot mix head generations. Any existing guidance append also takes the organization lock before revision insert, so guidance selection follows the same order. No transaction acquires a run/head lock and then waits for the organization lock. Commit the claim transaction before the first provider call; preserve the existing lease/fence predicates on the run update. Existing guidance pinning retains `{}` as its claimed-with-no-guidance sentinel. Never overwrite either non-null snapshot. Fenced `beginStep` remains immediately before each model call, and the ledger write remains before checkpoint.

Migration is additive. Add the new tables and nullable snapshot with no rewrite of historical runs. Deploy schema first, then worker/API code, then UI; keep built-in source as the default for every organization and role. A pre-upgrade live run with `template_snapshot = NULL` **and any existing step checkpoint** is a legacy partial run: its first new-worker claim pins the built-in baseline for all five roles, retaining its existing guidance snapshot, regardless of newly active templates. This prevents mixing a new role template into an already started pipeline. Preserve the pre-feature built-in instruction baseline in the rollout until all such runs have pinned or terminated; if that cannot be guaranteed, block activation until they drain. A pre-upgrade unstarted queued run has no step checkpoint and may pin heads active at its first new-worker claim. Already terminal runs are not retroactively attributed.

Activation stays disabled until all old worker processes are drained and the deployed code can pin complete snapshots. Store an activation-enabled release epoch in the database, default false; the deployment step sets it only after stopping old workers, confirming their generation jobs have no live handlers, and confirming the new worker version advertises snapshot support. The API checks this durable gate inside activation's transaction, not an operator assumption. The gate also remains false if a legacy partial run cannot be resumed under the preserved baseline. New workers can claim those partial runs while the gate is closed. An unknown snapshot format, missing role/channel entry, mismatched source or instruction SHA-256, impossible default/revision marker, unexpected extra key, invalid typed receipt, or oversized stored instruction fails permanently before any paid call. Validate the same full shape for decision attribution; never fill a hole with today's active head or infer a revision from a hash.

## Reporting

Add a separate `prompt_decision_template_revisions` child of the existing `prompt_decisions` journal, with one immutable row per decision and role: same-organization `org_id`, role, nullable template revision ID/version, explicit `is_default`, and the copied decision time. Copy it from the claimed run snapshot in the same content transaction as the decision. Attribution retains the existing **one `ai`/`full` master-version anchor**, matching producing run ID, and same-organization run linked to that content item; a second full master or missing link leaves the decision unattributed. Validate the complete template snapshot shape and SHA, then verify a revision's ID/version/hash against the immutable row in the same organization and role. Keep existing `prompt_decision_revisions` guidance links untouched: guidance evidence is checked independently, so bad template evidence does not erase valid guidance attribution and vice versa. Do not fabricate historical rows or acquire a late run FK lock after the item lock.

`GET /api/prompts/brands/:brandId/:role/templates/outcomes?days=30&cursor=<version>` adds a **separate template cohort**; guidance outcomes retain their endpoint and semantics. The DTO has `brandId`, `role`, `days`, `activeRevisionId` (nullable), `default` outcome row, up to 100 revision outcome rows ordered by version descending, and `nextCursor` using `version < cursor`. Each outcome row contains `kind`, revision ID/version or the default marker, `runCount`, `succeededRuns`, `publishedRuns`, current-item status counts, `withoutCurrentItem`, and approved/rejected review-act counts. The default row is returned on every page but never included in the cursor. `GET /api/prompts/:role/templates/revisions/:revisionId/usage?brandId=<id>&days=30` addresses a revision older than the current page with the same scoped counts. Head activation changes only the `activeRevisionId` display: old revisions and default keep their historical pinned-run counts; an inactive revision is never hidden or reattributed. Scope every query to the same organization and brand, use run creation time for the 7/30/90-day cohort, and join decisions only through independently verified links for runs in that cohort. Count each run once for a live published receipt even with two platform publications; review acts may outnumber runs. A role pinned on a run might never reach the model, current draft state is a present-time observation, and neither guidance nor template outcomes are quality scores or experiments. A default cohort includes only runs with a valid claimed default marker, not all historical runs lacking a snapshot.

## Settings interaction

Keep this under **Settings → Generation guidance** as a clearly labelled “Role templates” section or subordinate tab; no new global navigation destination. Show the role selector, active source (`Built-in` or revision/version), cursor-paged revision history with **Load more**, and a separate unsaved draft editor. Switching roles with unsaved changes warns before discarding. **Preview** is a secondary action and shows the fixed fixture, rendered body, and sample full-instruction size; **Save** creates an immutable draft; **Activate** is a separate explicit action for a saved revision and explains that it affects future first claims. Restore an earlier revision by activating it; **Use built-in** activates `null`. Do not call saving “activation.” On 409, show the newly active revision and keep the user's unsaved text; require a fresh explicit activation. Use one top-right primary action per form state, not multiple competing primary buttons or a bottom submit. Put history, fixture detail, and outcome inspection behind the shared `Advanced` disclosure where appropriate. Empty history teaches “Save” and still offers built-in preview. All controls have keyboard labels, loading/success/refusal states, inline errors with a focusable summary on failed validation, and translated server error mapping. Add EN source messages and matching ES/RU/PT keys, preserve message parity, and retain the current observational caveats beside outcomes.

## Acceptance criteria

1. Manager authorization and tenant isolation cover every read and mutation: foreign organization/role revision IDs return 404, a member cannot fetch source or preview it, and the composite FK rejects a mismatched active pointer even via direct SQL.
2. Two managers racing activation produce one winner and one 409; a claim racing activation observes one complete head set. The loser sees the new head. A saved draft remains inactive; rollback and built-in restoration mutate no revision.
3. Preview of unsaved text renders with the disclosed fixture and makes zero provider calls, ledger writes, and template writes. Preview/save reject syntax and source/render limits; a real oversized wrapper+guidance+template combination fails the 96 KiB bound at claim before a paid call. Replacement values containing token delimiters never expand again.
4. Golden fixtures pin byte-identical default `instructions` for every role, content type, and adapter platform. Tests pin separate nonce-fenced `prompt` material, immutable schemas and protected rules. Brief, pasted source, prior step output, news, and knowledge never enter the template fixture or `instructions`.
5. Change brand voice/language, channel name/platform, template head, and guidance between claim and resume, including an interleaving during context loading. The resumed role instructions, adapter schema limit, and postprocessing use the same frozen receipt. A deploy changing wrapper/policy code leaves the stored instruction bytes unchanged; an incompatible engine version fails closed.
6. A malformed snapshot (one missing role, extra key, bad default marker, SHA mismatch, missing adapter entry, or altered typed receipt) fails before a paid call and cannot be used for attribution. Test each corruption separately so one guard is the sole reason for refusal.
7. Migration tests cover default-only organizations, Better Auth-created organizations with absent lazy heads, pre-upgrade unstarted queued runs, partial runs forced to baseline despite active templates, and old terminal runs. The durable rollout gate refuses activation while an old worker or incompatible partial run remains.
8. Template outcomes have a default row and cursor-accessible revisions past page 100. Tests show active-to-old transitions do not rewrite historical cohorts, exclude unclaimed/historical runs, distinguish guidance and template IDs, and count two publication receipts once.
9. Decision attribution tests retain the one-full-AI-master/linked-same-org-run anchor, event order, and independent guidance/template evidence. Mutate each missing/wrong evidence field separately, including wrong tenant, wrong role, wrong hash, second full master, and wrong linked run, to prove the intended refusal cause.
10. Settings tests cover explicit Save versus Activate, stale conflict, restore/default, unsaved edits, localized refusals in a non-English locale, four-locale key parity, keyboard focus on error, and the one-place/one-primary-action layout.
