# Versioned role templates

**Status:** design for review. This adds the remaining active legacy capability: a manager can edit, preview, activate, and restore the role instruction body used by generation. It does not import the legacy global `cf_prompt_templates` table, Jinja2 interpreter, mutable rows, automatic prompt selection, or performance score.

## Starting point and boundary

Pubrick already has immutable **additional guidance** revisions in `prompt_revisions`, shown in Settings → Generation guidance. The greatest guidance version is active, and `pipeline_runs.guidance_snapshot` pins its exact text at the first successful worker claim. Guidance usage, review decisions, and brand outcome reports are observational. This feature keeps those contracts and names the new object **role template** throughout the API and UI so a guidance revision can never be mistaken for a template revision.

The five roles are `researcher`, `writer`, `editor`, `factcheck` (labelled “Claims to verify”), and `adapter`. A template replaces only the editable role prose now interleaved with `spec.role` in `packages/ai/src/steps`; it does not replace `defineStep`, `instructionsFor`, `materialFor`, `contentTypePolicy`, the step's Zod schema, model-call options, or the worker's fencing, metering, and checkpoints. Implementation first extracts the load-bearing role rules into code-owned text: researcher has no web verification and invents no facts; writer uses supplied material without copying long passages; editor removes unsupported claims; factcheck lists claims without verifying them; adapter preserves meaning, adds no claims, and obeys the shared channel limit. The adapter has one organization-wide role template rendered for each selected channel, not an independently active template per channel. Existing guidance is appended after the selected template as today. Protected role rules and content-type policy are emitted outside the editable body, after it, with explicit precedence over it. The code-owned wrapper retains the date, brand configuration, untrusted-material warning, JSON-only instruction, and channel identity/limit rules. A template may add editorial direction but cannot remove those rules by omission.

This is a prompt boundary, not a claim that a model always obeys the higher-priority prose. Validation checks syntax and size; it cannot prove the semantic safety or quality of manager-written instructions. The structured-output schema, length checks, source-quote validation, provenance calculations, human involvement gate, and human publication approval remain executable server rules. In particular, “Claims to verify” never becomes verified claims, supplied source text never becomes independent evidence, and no UI copy claims originality.

## Data and authorization

Add `role_template_revisions`: `id` UUID, `org_id` non-null FK, closed `role`, positive `version`, `source` text, `source_sha256`, `created_by` nullable user FK, and `created_at`. Unique `(org_id, role, version)`; source and its hash are immutable after insert. Add `role_template_heads`: one row per `(org_id, role)`, `active_revision_id` nullable, and nonnegative `generation` used for compare-and-swap. Seed five default heads per organization at migration and organization creation with `active_revision_id = NULL, generation = 0`. `NULL` means the built-in source. An FK or repository check must ensure the active revision has the same organization and role; the repository is the only path for switching it. Do not model activation by mutating `is_active` flags on revisions. Do not delete revisions while their organization exists; run snapshots and decision history remain intelligible after rollback. Both tables are organization scoped, and every repository method takes `orgId` first and uses explicit selected columns.

The existing guidance table, its implicit latest-version behavior, and its endpoints remain distinct. Template source is never stored in guidance. The API uses `ActiveOrgGuard` and the existing manager brand scope (`owner`/`admin`) for **every** template list, history, preview, create, activate, usage, and outcomes request. A foreign revision ID returns 404 for the active organization or role. No cross-tenant template text, count, preview, or existence hint is returned. General members cannot read template source through these endpoints.

## Revision workflow and API

`GET /api/prompts/templates` returns the five roles with active revision metadata or `default`, head generation, and the built-in source for an authorized manager. `GET /api/prompts/:role/templates/revisions` returns the latest 100 immutable revisions, newest first; older revisions remain addressable by ID. `POST /api/prompts/:role/templates/revisions` with `{source}` creates a draft and returns its ID/version. It does **not** activate it. Version allocation serializes on the organization row, as guidance creation does, and inserts once; identical text may still be a new auditable revision only when explicitly saved. Reject blank source, because built-in behavior is selected by activating `null`. Normalize CRLF to LF before length/hash validation; never silently trim meaningful spaces. Store the source exactly as normalized.

`POST /api/prompts/:role/templates/preview` takes `{source}` directly from the unsaved editor. It validates and renders entirely on the server using a fixed public sample fixture, returns rendered role-body text, referenced variable names, and size; it makes **no Gemini call**, consumes no BYOK key, writes no usage ledger row, and saves nothing. The response labels it a syntax/render preview, not an output sample or safety test. The same validator and renderer run before draft creation and at worker use; a corrupted stored revision causes a permanent pre-provider run failure with a closed error code rather than repeated paid retries.

`PUT /api/prompts/:role/templates/active` takes `{revisionId: uuid | null, expectedRevisionId: uuid | null, expectedGeneration: number}`. `revisionId: null` restores the built-in default. Under a transaction, lock the head, compare **both** expected values, verify the target revision belongs to this organization and role, and atomically update the pointer and increment generation. Return 409 with the fresh head on a stale edit; never silently overwrite another manager's activation. A rollback is the same operation targeting an earlier revision. Re-activating the current target with a matching expectation is idempotent and does not increment generation. There is exactly one active choice per role; creating a draft never changes running or future generation until activation succeeds.

## Template language and bounded rendering

Use a deliberately small **one-pass variable substitution**, implemented as a fixed token scan in `packages/ai` rather than an interpreter dependency. The workspace has no templating dependency; Mustache and Handlebars would admit a broader language (sections/helpers/partials or escaping semantics) that this feature must reject. A scanner over the exact `{{name}}` token form and a closed variable map is shorter than configuring and then defending those languages. This is the narrow product-owned grammar, not a general parser. There are no conditionals, loops, filters, expressions, dot paths, includes, partials, environment access, helper registration, HTML escaping, or recursive expansion. A replacement value containing `{{...}}` stays literal; never pass it through a second render.

Allow only `{{current_date_utc}}` (ISO date), `{{content_type}}` (validated run enum), and `{{content_language}}` (validated language code) for all roles. The adapter alone also permits `{{channel_platform}}` (closed platform enum) and `{{channel_limit}}` (integer from the shared platform limit). Do not expose brand voice/name, channel name, credentials, user brief, pasted source, knowledge, news, previous model outputs, or arbitrary run JSON as variables. Brand and channel configuration that the current code already places in `instructions` stays in the code-owned wrapper, not in the variable map. No variable reads the process environment or database by name.

The preview fixture is constant and disclosed next to the preview: `2026-01-15`, `social_post`, `en`, and, for adapter, `telegram` with its actual shared limit. It contains no real tenant data. Runtime values are taken from parsed, typed run/channel receipts at claim, with the claim date in UTC; the adapter values are frozen for each selected channel. Unknown tokens, malformed braces, unsupported syntax, missing values, NUL/control characters other than LF and tab, and invalid UTF-8 input are refused with a field error identifying a position and allowed variables. Literal braces must use a documented escape form (`\{{` and `\}}`); that escape is removed in one pass. Bound normalized source to 12,000 Unicode code points and 48 KiB UTF-8, rendered role body to 16,000 code points and 64 KiB, and the final `instructions` string to 96 KiB before any provider call. A template has no recursion or expansion of rendered text. Bound request body size before parsing as well. These limits apply identically to preview, save, claim, and call.

## Run pinning and migration

Add nullable `pipeline_runs.template_snapshot` as an immutable object keyed by all five roles. `NULL` means never pinned. The first successful claim writes all five effective template selections in the **same fenced claim update** that changes the run to `running`: revision ID/version or `null` for built-in, exact normalized source, SHA-256, and a snapshot format version. Even a default selection stores its built-in source, rather than an empty object that might pick up a later deployment's changed default. The claim also freezes the small typed render values, including each selected adapter channel's platform/limit, so preview/render semantics cannot drift within a run. Do not store a rendered material block or duplicate untrusted input in this snapshot. On lease takeover, queue redelivery, or checkpoint resume, `COALESCE` keeps the prior snapshot and all unfinished steps render from its source and values. A “Try again” action creates a new run and pins the then-current heads. A queued run claims after activation and uses the newly active source; a claimed run does not change when a manager activates, rolls back, or edits another revision.

The claim and activation must have a clear ordering: read active heads and immutable revisions as one database snapshot while updating the run row, so activation either precedes the first claim or follows it. Run claim must not use separate per-role reads that could mix head generations. Existing guidance pinning stays in the same claim path and retains `{}` as its claimed-with-no-guidance sentinel. Never overwrite either non-null snapshot. Fenced `beginStep` remains immediately before each model call, and the ledger write remains before checkpoint.

Migration is additive. Add the new tables and nullable snapshot with no rewrite of historical runs. Deploy schema first, then worker/API code, then UI; keep built-in source as the default for every organization and role. Runs claimed before the upgrade have `template_snapshot = NULL`: on their first claim after upgrade, snapshot current effective templates while preserving the existing guidance snapshot and checkpoints. Already terminal runs are not retroactively attributed. During mixed-version rollout, do not enable activation while an old worker can claim runs without a template snapshot; use a deploy-time capability gate or drain old workers first. A new worker must treat a live run with a non-null old guidance snapshot but null template snapshot as an upgrade resume and pin once. If an old worker can still accept an active template, refuse activation until it is drained. Document the snapshot version and provide a fail-closed path for unknown versions; never silently use today's active head on a resume.

## Reporting

Add a separate `prompt_decision_template_revisions` child of the existing `prompt_decisions` journal, with one immutable row per decision and role: same-organization `org_id`, role, nullable template revision ID/version, explicit `is_default`, and the copied decision time. Copy it from the claimed run snapshot in the same content transaction as the decision. The ID/version must belong to the same organization and match immutable revision rows; conflicting or missing evidence stays unattributed. Keep existing `prompt_decision_revisions` guidance links untouched and do not fabricate historical rows. `GET /api/prompts/brands/:brandId/:role/templates/outcomes?days=30` adds a **separate template cohort** selected by template revision or built-in default and role; guidance outcomes retain their endpoint and semantics. Label every number as observational: denominator is pinned runs started in the selected 7/30/90-day window, including failures; a role pinned on a run might never reach the model; approvals/rejections are human acts and may outnumber runs; current draft state is a present-time observation; publication is counted at most once per run with a live receipt. Do not combine guidance and template revision IDs, assign a quality score, infer causation, or revive legacy A/B selection. A default cohort is bounded to runs with a claimed default marker, not all historical runs lacking a snapshot.

## Settings interaction

Keep this under **Settings → Generation guidance** as a clearly labelled “Role templates” section or subordinate tab; no new global navigation destination. Show the role selector, active source (`Built-in` or revision/version), a latest-100 revision history, and a separate unsaved draft editor. Switching roles with unsaved changes warns before discarding. **Preview** is a secondary action and shows the fixed fixture and rendered body; **Save** creates an immutable draft; **Activate** is a separate explicit action for a saved revision and explains that it affects future first claims. Restore an earlier revision by activating it; **Use built-in** activates `null`. Do not call saving “activation.” On 409, show the newly active revision and keep the user's unsaved text; require a fresh explicit activation. Use one top-right primary action per form state, not multiple competing primary buttons or a bottom submit. Put history, fixture detail, and outcome inspection behind the shared `Advanced` disclosure where appropriate. Empty history teaches “Save” and still offers built-in preview. All controls have keyboard labels, loading/refusal states, and translated server error mapping. Add EN source messages and matching ES/RU/PT keys, preserve message parity, and retain the current observational caveats beside outcomes.

## Acceptance criteria

1. Manager authorization and tenant isolation cover every read and mutation: foreign organization/role revision IDs return 404, and a member cannot fetch source or preview it.
2. Two managers racing activation produce one winner and one 409; the loser sees the new head. A saved draft remains inactive; rollback and built-in restoration append no mutation to a revision.
3. Preview of unsaved text renders with the disclosed fixture and makes zero provider calls, ledger writes, and template writes. Preview, save, claim, and use reject the same unknown/malformed tokens and size violations. A literal replacement value containing token delimiters never expands again.
4. Tests pin the exact model `instructions` and separate nonce-fenced `prompt` for every role. Brief, pasted source, prior step output, news, and knowledge never enter the template fixture or `instructions`; schema, content policy, channel limit, claim labelling, provenance, and human approval stay enforced even if editable prose conflicts with them.
5. Claim/activation race tests prove one coherent five-role snapshot. In-flight runs keep exact source and typed values across activation, rollback, lease takeover, and checkpoint resume; new runs use the new head. A corrupt/unknown snapshot fails before a paid call.
6. Migration tests prove default-only organizations, pre-upgrade queued and partially executed runs, and old terminal runs behave as stated. Rollout prevents active templates while an old worker can claim without pinning.
7. Template outcome and review attribution tests distinguish template IDs from guidance IDs, exclude unclaimed/historical runs, preserve same-org evidence and event order, and avoid counting two publication receipts twice.
8. Settings tests cover explicit Save versus Activate, stale conflict, restore/default, unsaved edits, localized refusals in a non-English locale, four-locale key parity, and the one-place/one-primary-action layout.
