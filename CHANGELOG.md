## [Unreleased]
### Fixed
- The last three screens read the refusal codes the API had already started sending. The post screen — where the publish gate refuses an unread AI draft and a pinned post refuses an edit, the two sentences a reviewer is most likely to be shown — the run receipt's Cancel, and both brand screens were still rendering the API's English, because `errorMessage`'s translator argument was optional and they passed two arguments instead of three. That does not fail: it silently falls through to the server's sentence, which looks correct to an English reader and is English to everyone else. All seven call sites now pass one, including the four that are not the obvious one — each screen's poll, and the verdict beside a channel's Test button, which are separate calls that a test of the button path leaves untouched. The argument is now REQUIRED, so the next screen cannot forget it, and a test asks the compiler directly (a two-argument call must be rejected as an arity error, with the three-argument call beside it compiling clean, because `@ts-expect-error` is satisfied by any error at all).
- "No active organization" is a code on the wire instead of a guess about English prose. The browser decided whether to send an account to onboarding by matching `/no active organization/i` against the sentence in a 403 body — prose written for a developer's network tab, in the one product that translates everything else — so rewording it, or translating it, would have stranded an account on a screen it can never load, with no error anywhere. `ActiveOrgGuard` now throws that refusal with `no_active_organization` beside the unchanged sentence, and the web reads the code and nothing else: deliberately not a code-or-sentence fallback, since a fallback keeps working with the code removed and pins nothing. The guard's other 403 — a session pointing at an organization the caller is not a member of — stays uncoded on purpose, and is asserted to be, because one code shared by both would loop that account through onboarding and back.
- Every refusal a person can provoke now reaches the browser as a code, and is read in the reader's own language. The web renders a 4xx body verbatim by design — the detail is the whole value of it — but those bodies are English sentences written by the API, so the publish gate's two refusals, every conflict about what may be edited or approved, the run admission cap and "this brand has no channels" were English in a product that ships in four, while a test guarded message parity across all four. They also spoke a different vocabulary: the server said "content item" where every screen says "post". Twenty-five refusals now carry a code beside the sentence, which stays where it is because a developer's network tab, a public-API consumer and a web build older than the code all still need it. Codes are nullary: a status is in the code's name (`content_pinned_approved` against `content_pinned_published`), and the one number a sentence needs is `MAX_CONCURRENT_RUNS`, which both sides already import. A code this build has never heard of — a released server against a cached client — falls back to the API's own English rather than to a generic apology, because that sentence is ours and cannot be quoting a provider's key. One wire field name reached users, "scheduledAt: scheduledAt must be in the future"; it turned out not to be validation at all — a clock-reading predicate is false a moment after it parsed — so it moved out of the DTO into the domain and became `schedule_in_past`, and the rest of the boundary answers with one honest sentence that names no field.
- The bot-token redaction is guarded for the first time. It is the only thing between a token and a browser — a token echoed in a platform error reaches the adaptation's error field, which the API returns and a screen prints — and both of its halves were deleted without a single test failing. The one test that looked like its guard put the token in a URL, the single shape both passes strip, so it pinned only that at least one of them ran. Each half now has a shape the other cannot match, asserted on the error text the worker stores and on the reason the channel test returns.
- An expired, revoked or already-accepted invitation no longer opens invite-only registration, and all three answer exactly as a stranger with no invitation does, so a dead invitation cannot be used to find out that an account once existed.
- Eleven more guards this branch added are now observed by tests rather than only by their authors. Among them: the ordering that decides which delivery receipt a screen reports, which was the very class an earlier commit here exists to close; the arm that marks an item failed only when its last channel does; the two-minute call budget, which was dropped entirely whenever a caller passed a signal of its own; and the half of the modal's focus trap that pulls focus back in. Two of these turned out to hide real gaps rather than missing tests: the adaptation lock's ordering survived all ninety tests of its package, and nothing stopped an approval re-enqueueing an adaptation whose send was already in flight.
- Two end-to-end tests waited for a lock by watching the database for a blocked query and matching on its text — and the two files run at once and issue byte-identical statements, so each could have returned on the other's waiter. They now identify themselves per connection and fail loudly rather than passing on the wrong evidence.

### Added
- `scripts/mutation-check.mjs` and `docs/mutation-testing.md`. A verification pass over this branch found fifteen guards whose authors had each reported them pinned, in good faith, and separately reported that the database-backed suites answered the same mutation differently on different runs. The second claim did not survive measurement — twelve runs of each suite, quiet and under load, gave byte-identical outcomes, and the reviewer had been watching five agents share one machine — but the first did. The script runs a suite N times and names a verdict only when every run agrees, refusing to answer at all when the runs disagree, when a kill comes from a different test each time, or when the database variable is missing and every database test would silently skip. It does not prove determinism, and the document says so: a flake rarer than one in N still reads unanimous.

- Deleting a channel no longer deadlocks the publish worker, and cancelling a delivery no longer returns a server error. Two lock cycles, both reproduced on Postgres. The channel delete took the channel and then its adaptations; the worker held an adaptation and took a foreign-key lock on the channel when it wrote a delivery receipt — and each side had documented its order carefully, against a different counterparty, each silent about the third table its own statements touched. Separately, the new sweeper for stuck deliveries updated rows in one unordered statement while rejection took the same rows in id order, re-opening by accident a deadlock this project had already closed on purpose. There is now one order for the whole product, written down in `docs/lock-order.md` with what counts as taking a lock — foreign keys, cascades and delete triggers included — and referenced from all four sites.
- A delivery attempt can no longer release a claim that is not its own. The rule was stated in words one screen above the code that broke it: a write whose fence does not match leaves the claim standing, because releasing another attempt's claim is how a duplicate post gets sent. The release ran first, unfenced, and deleted whatever it found. A claim is now addressed by its own row, so an overtaken attempt releases nothing — and the same hole in the success path, which no review had named, was found by mutation and closed with it.
- A post that went live while its channel was being deleted no longer leaves a receipt with nothing in it. The claim was written before the call, the platform accepted the post, the delete cascaded the adaptation away, and the write that would have filled in the id and the link matched no rows and returned. The receipt now records the post it can still prove, with its id, its link and the channel's name; a claim whose attempt never came back is resolved by its own sweep, since nothing driving off adaptations can reach it.
- Our own two-minute call budget no longer reports itself to the user as "cancelled" and no longer ends a run that would have resumed. A timeout expiring inside the model SDK's retry backoff arrives as the same bare exception a user's cancellation does, so it took the cancellation's path — permanent, and named with the one word that was never true, since nothing in the product cancels a call. The budget now records which signal fired first, and the classifier reads that rather than guessing from the exception.
- The guard that stops the test suite going dark can no longer be walked past. It discovered gated files with a pattern and silently dropped what the pattern did not match, so a gate written in an unfamiliar shape was simply not in the set — the guard passed, which is the opposite of the property it exists to have. It now parses each spec file with the TypeScript compiler and classifies it as unconditional or gated on a declared variable; anything that could stop a suite and resolves to neither fails the run by name. Eleven evasions that the pattern missed are each now caught.
- A session that dies while a screen is polling now takes the person to the login screen. The shell's guard was driven only by the session store, and nothing invalidated that store when the API answered 401 — and the library refreshes on tab-visibility and network events, neither of which fires for someone watching the tab. The two screens that poll would paint a red sentence and stop, with no redirect and no link.
- The contrast ratchet now derives which grounds a colour is actually painted on, by parsing every class list in the app, instead of trusting a hand-kept list of pairs. A token that gained a second ground silently kept the verdict its first ground earned; three had, including one exempted "as a ground" while being the letter in an avatar.

- A model call that was dispatched and then lost is no longer recorded as free. The meter's `catch` threw the error away and wrote a zero-token, unpriced row, and the spend query files those under "cost is known to be zero" — correct for a 429 the provider refused before generating, wrong for a timeout, a socket reset, or a body the provider's own schema could not parse, because a completed generation is billed whether or not the client received the answer. Measured on Postgres: one priced call plus three lost ones rendered `≈ $0.007875` against a true `$0.0315`. `usage_ledger.outcome` now records `completed | refused | unknown`, classified where the error still exists, and both readers — the SQL aggregate and its TypeScript twin — count an unknown outcome as unpriced, so the figure reads `≥` with the count instead of an estimate that hides a quarter of the bill. Only a non-2xx status is a refusal: the SDK throws with status 200 on an unparseable body. Every call now carries a two-minute budget for the whole logical call, so a hung provider is bounded in minutes rather than the HTTP client's five-minute default multiplied by every retry.
- A send whose outcome we never learned is no longer retried as if it never happened. A fetch that failed *after* the request body left — a socket reset, the adapter's own timeout, a gateway error on the reply — was classified transient and rethrown; the queue retried, nothing had been recorded, and the post went out again: two messages in the channel, one row in the database, no error anywhere. A `publications` row is now claimed *before* the platform call under its own partial unique index, so a claim that outlives its attempt **is** the evidence that the outcome is unknown. Known-not-posted failures (the platform's own error envelope, anything thrown before the fetch) hand the claim back and retry as before; everything else ends terminally as `unknown`, with a sentence asking a human to check the channel before re-approving.
- A run whose queue job was completed underneath it is no longer a run left running for ever. The queue re-inserts a failed job under the same id, so a re-dispatch by heartbeat lets a displaced handler's ordinary return complete the *live* handler's job; the live handler's next transient error then failed nothing, retried nothing, and dead-lettered nothing. Observed: a run stuck at `running`, holding a slot against the concurrency cap, with one step billed twice. A sweeper now fails runs left running with an expired lease and no live job behind them, as a single guarded statement that re-evaluates under the row lock — so a handler that is merely slow wins the race and keeps its run. The publish queue has the same shape and its own sweeper, which reads the in-flight claim: a claim that outlived its attempt becomes `unknown`, never a flat failure, because a flat failure invites the re-approval that posts a second copy.
- The approve and publish paths now lock the item they are deciding about. Three races, all reproduced: two channels publishing at once each saw the other still in flight and neither promoted the item, leaving a fully published post reading *Approved*, uneditable, and rejectable; an approval arriving while the last channel's write was open wrote `approved` over `published`; and an edit already holding the item's lock landed *underneath* an approval, so text nobody had read went out and the approval pin then refused to let the reviewer revert it. The comment that justified the missing lock — that taking it would invert the lock order — was wrong, and adding the lock it warned against produces a real deadlock, which is now the test that proves the order.
- A run's failure reaches the browser as a code, not as the provider's own sentence. The credential Test button already returned a closed set of verdicts *because* providers quote the submitted key back in their error bodies; the generation path built both its error classes from the provider's message verbatim, wrote it to the run row, returned it from two endpoints and printed it on the queue strip. It is now one of thirteen codes, translated in four languages, with the prose kept to the worker's log and the key redacted there by literal and by shape.
- Rotating a bot token no longer destroys what it published. There was no way to change a channel's credentials except to delete it, and the delete cascaded every adaptation and every `publications` row — the durable record that a platform accepted a message, with its id and its link — while the spend ledger deliberately survived the same delete. Publications now outlive their channel: both foreign keys null out and a database trigger stamps the channel's name and platform, because a brand delete reaches channels through a cascade with no application code in the path. `PATCH /api/channels/:id` rotates the credentials in place, deleting a channel or brand cancels its outstanding jobs in the same transaction, and the next send reads the new token.
- A re-approval can no longer be overwritten by an attempt that already ended. The retry-exhausted path read the adaptation's status and then wrote unconditionally, so a reject and re-approve landing in between left the freshly re-approved row failed with its attempt count bumped, and its live job then found a failed row and completed having sent nothing — the user's action vanished with no error. The guard is in the statement now, fenced on the status and attempt count the job id keys on.

### Added
- `SIGNUP_MODE` — `open`, `invite` or `closed`. Left unset, an instance is open while it has no accounts and closes itself once the first one exists, so the step nobody remembers (turning registration back off) is not a step. Registration was open, unverified and unbounded on a product whose own self-hosting guide says to put it on a public URL, and the per-organisation concurrency cap caps nothing for a stranger who creates several organisations.
- Delivery has a third outcome. `deliveryOutcome` on every adaptation the API returns distinguishes a post that went out, one that failed, and one whose fate is unknown — a server-computed verdict rather than a raw column, so the queue and the item screen cannot answer the same question differently.

### Changed
- The database tier of the test suite can no longer switch itself off behind a green badge. Fourteen files were gated on a database URL and both global setups returned early without one, so 209 of 885 tests — every tenancy, publish-gate, fence and ledger test — skipped with exit 0 whenever that variable failed to arrive, including when it was exported in the shell but not declared in the build config. A guard in each database-owning package now discovers the gates by reading its own package's specs, and fails on a gate whose shape it cannot parse or whose variable is undeclared: a new silent gate cannot be introduced, which closes the class rather than the instance. CI runs the suite forced and serial, as the local rule always required and the workflow never did.
- Signing out signs you out: one hook for all three call sites, a redirect to the login screen, and the application shell now refuses to render for a session that resolved to null, sending the visitor to login with a return path. Previously the URL did not change, the organisation's AI-provider row and its Save button stayed on screen, and a signed-out visitor to the queue got the whole shell plus "Your session has expired" — untrue, since they had signed out.
- The screen that pressed the button watches until the send is over. Approving re-read once and then stopped, so a delivery that failed two hundred milliseconds later still read *Approved · Queued* eight seconds on, and only a reload showed otherwise. Both the item screen and the queue now poll while any adaptation is in flight, and stop when none is.
- The shipped API image runs in production mode with its rate limiter enabled explicitly rather than inherited, and keys it on the real client behind the proxy. Twelve wrong passwords in a row previously returned twelve refusals and no limit; a forged forwarding header bypassed the limiter entirely.
- The price table knows every Gemini family the product can reach, matched by tier after normalising the id, each rate verified against the published pricing page and carrying its own effective date. It previously knew exactly one identifier, so any other choice reported "cost not reported" for ever. Families whose existence could not be confirmed are left unpriced deliberately: an honest gap beats a confident wrong number.
- Colour: the accent is re-lit per ground rather than desaturated, the button label is its own token, and the danger colour — never defined for the dark theme, and sitting at 2.99:1 — is now readable. A test parses the token file and asserts a ratio for every pair the app paints, in both themes, and fails when a new token arrives with neither a pair nor a written exemption.
- The database now enforces what the code assumed: one live adaptation per item and channel (a duplicate previously produced two live publish jobs for one channel), a check constraint on every column whose values the schema enumerates, and a composite key tying a version row to its own adaptation. The migration refuses and names the offender rather than failing on a constraint violation nobody can read.
- Ten tenant filters that were correct but observed by nothing now have tests, each proven by deleting the predicate and watching a named test go red. A scan fails when a list endpoint has neither a cross-tenant test nor a written reason.
- Keyboard: the modal traps focus instead of letting four tabs walk out behind the overlay; the menu and the segmented control implement the roving-focus patterns their roles claim; destructive actions in Settings and on the brand screen confirm first; three read paths that swallowed their errors now say a load failed instead of showing an empty list.

- A save that turns a newline into a space now leaves the version row it always should have. "Did the body change" had two definitions: the version writer compared whole bodies through `normalizeForComparison`, which collapses every whitespace run, while the publish gate and the origin badge split into sentences first — and a newline is a sentence boundary. On line-structured social copy those disagree about exactly one keystroke: replacing a U+000A with a space wrote no `content_versions` row and yet turned the gate's 409 into an approval, so the model's adapted text published byte for byte with nothing in the database naming the human act that authorised it. Both now ask `isSameText` (`@pubrick/shared`), which answers with both lenses — a save that can move the gate's verdict always leaves a row, and so does a reorder, which the gate cannot see but a history has to be able to restore.
- `@UserId()` raises its own explained error for a request carrying a session with no `user`, instead of a bare `TypeError` from inside the decorator that Nest reports as an unexplained 500. Its value is written to `content_versions.created_by`, so the failure has to be loud: a NULL author is exactly what an AI-written row looks like.
- The publish gate now looks at AI text that lives only in a channel. It was entered on the ITEM's origin, so a draft a human typed whose per-channel text the model wrote skipped every check and could be approved with nobody having read the words that actually publish (`adaptations.body` is what the worker sends). It is entered now whenever an `ai` version row exists for the item **or any of its adaptations** — the item's own origin still admits an `ai` item whose version rows are missing, because no evidence must refuse rather than walk out of the gate. The refusal says something different for the shape this reaches: with no complete `ai` version of the body, "is every sentence still the model's" answers yes for every possible body, so editing can never lift the refusal and the message no longer offers it — it names opening the item, the recovery that always works.
- A carriage return in a body no longer breaks the provenance lens. A `<textarea>` strips CR from its API value while the React string the overlay slices keeps it, so a CRLF body — which `POST /api/content` stored verbatim, as did the MCP server and any script — made the two layers render different character streams: every highlight after the CR slid off the words it described, the counter reported a length the field did not hold, and React's `onChange` reads the DOM's normalised value, so one keystroke anywhere silently rewrote every CR out of the document. `contentCreateSchema`, `contentUpdateSchema` and `adaptationUpdateSchema` now pipe `body` through `normalizeNewlines` (normalise first, bound by `MAX_BODY_LENGTH` second, so the limit measures what is stored), which covers the publish gate, the mask and the overlay at once; `DimmedTextarea` normalises again on the way to the screen for text that arrived by another road.
- The origin badge tells the same story on a queue card as on the item screen. A rewritten AI draft read "AI-drafted" in the queue and "Human-edited" one click later, because the list carried no reference text to compare the body against — and "the badge already carries the claim at a glance on every card" is exactly the argument for shipping the lens off by default. Both endpoints now return `bodyIsAiVerbatim`, one boolean the API computes with `allSentencesAi` (`@pubrick/shared`) — the publish gate's own question, "is every sentence of this still one the model wrote" — so the queue can show the fourth badge without being sent every version body to draw four words, and the badge cannot answer differently from the gate on the same draft.
- The provenance lens says what dimming means: a short legend under the toggle, shown only while the lens is on. Without it the lens had an unreadable success state — turn it on, see nothing dim, and there was no way to tell "every sentence here is yours" from "the highlighting is broken". The legend also owns the one honest disagreement between the badge and the dimming: a deleted sentence is an edit the lens has nothing left to show, so the badge can read "Human-edited" while every visible sentence is dimmed.
- Signing in again no longer sends a returning member to onboarding to create a second workspace: a new session is born with `activeOrganizationId` set to the user's organization (earliest membership, read from their own `member` rows), instead of null. Previously only the sign-up → create-org flow set it, so every later sign-in looked org-less. A user with no organization still lands on onboarding, unchanged.
- `useToast()` no longer throws on first real use — `ToastProvider` is now mounted once in the signed-in app shell.
- The modal backdrop is no longer a second, identically-named "Close" control ahead of the dialog in the tab order: it stays clickable (closing the modal), but is now out of the tab order and out of the accessible name space, leaving the header button and Escape as the only close affordances a screen reader or keyboard user sees.
- The modal backdrop scrim and the wordmark's accent fill now reference real design tokens (`--color-overlay`, defined in both themes; `--color-accent`) instead of a raw `/40` opacity modifier and an undefined `--color-brick` fallback.
- `Textarea`'s character counter is wired to the field via `aria-describedby`, so assistive tech announces it.
- Brand/channel name fields and credential fields no longer duplicate their label as a placeholder; credential fields show only the humanized label, not the raw wire key as visible text.
- The brand detail page's title shows a `Skeleton` while the brand loads, instead of a permanently empty `<h1>` if the fetch fails.
- Default link color no longer overrides component text colors (the primary "Sign up" link on the landing page rendered white-on-invisible) — base anchor styles moved into `@layer base`.
- Hydration warnings from the theme boot script (`suppressHydrationWarning` on `<html>`) and from the Settings appearance control (stored theme preference now syncs after mount).
- The queue's status filter scrolls inside itself on narrow screens instead of widening the page.
- "Try again" on a finished run now dismisses the run it retries. The retried run stayed open, and failures sort first, so each retry left its predecessor's strip stacked above the run that was actually working — press it twice and the live run sat under two failures that would never change again.

- Auth: Better Auth email/password sign-up and sessions, proxied through the web app at `/api/auth/*`.
- Organizations: create/set-active, org-scoped tenancy (`org_id` on every tenant table).
- Brands: org-scoped CRUD with zod validation.
- Channels: org-scoped CRUD with AES-GCM encrypted credentials (`encryptJson`/`decryptJson`), never returned by any endpoint.
- Channel connection test endpoint: verifies Telegram credentials (`getMe`/`getChat`/`getChatMember`) without publishing anything.
- Content: drafts with per-channel adaptations, a review queue (approve/reject, immediate or scheduled), and body/adaptation overrides.
- Publishing: a Telegram adapter and a pg-boss-backed worker that publishes approved adaptations, classifying platform errors as permanent (recorded as `failed`, job completes) or transient (rethrown for pg-boss to retry), plus a DLQ consumer that terminates adaptations whose retries are exhausted.
- Env wiring for auth/crypto/publishing through turbo, CI, docker compose, and `init.sh`; self-hosting docs for `BETTER_AUTH_SECRET` / `APP_ENCRYPTION_KEY` / `PUBLIC_ORIGIN` and connecting a Telegram channel.
- Brand identity: wordmark (light/dark), brick mark and 1280×640 social card in `assets/`; README header with scheme-aware logo and badges; web favicon (`app/icon.svg`), inline `Logo` component on the landing page, and the palette as CSS custom properties in `app/globals.css`.
- Navigation between brands and the content queue (the landing page links to both), so the review-and-publish flow is reachable without typing a URL.
- Test coverage for `apps/web` (77 tests, from none): RTL pages/components against a mocked `@/lib/api`, `api.ts` and `orgSlug` unit-tested directly, and the proxy route matcher, all wired into `pnpm test` via turbo.
- A restyled web app: a token-based design system (`app/globals.css` + `components/ui/*` — Button, Card, Input/Select/Textarea, ListRow, StatusBadge, EmptyState, Menu, Modal, Skeleton, Toast, Advanced disclosure) applied across every screen (landing/auth, app shell with sidebar/rail/tab-bar, settings, content queue/compose/item, brands and brand detail), following the UX constitution in `CLAUDE.md` and the pattern dossier in `docs/ux-patterns.md`. A `/design` gallery route renders every component and token for review.
- PWA install support: a web app manifest (`public/manifest.webmanifest`) with 192/512 and maskable icons generated from `assets/mark.svg`, an apple-touch-icon, and light/dark `theme-color` metadata wired through Next's `viewport` export.
- Bring-your-own-key model credentials: one AES-GCM encrypted key per provider per organization (`PUT`/`GET`/`DELETE /api/ai-credentials`), never returned by any endpoint, managed from a new section on the existing Settings screen. A **Test** action (`POST /api/ai-credentials/:provider/test`) makes one minimal structured call and reports which model answered and what it cost — proving the key, the model id and structured-output support in a single act, never from a cache. A failed test answers with a classified code, never the provider's own sentence — provider error bodies quote the submitted key back, and the code is also what lets the verdict be translated. Removing a key fails that organization's queued generation runs with a message naming the missing key instead of leaving them to die on a provider 401. Settings also shows the organization's spend to date, summed by `org_id` alone and rendered under three rules that stop a nullable `SUM()` from printing a confident wrong number: any unpriced call makes the figure a floor (`≥ $X`), any locally-estimated call makes it approximate (`≈ $X`), and only provider-reported costs make it exact. A round trip the provider rejected before counting any tokens — a 429, a connection reset — is ignored rather than counted as unpriced: its cost is known to be zero, and the ledger is lifetime, so one blip would otherwise stamp `≥` on an organization's total forever.

- Generation runs are executed by the worker: one pg-boss job per run drives the five roles (researcher, writer, editor, fact-checker, and one adapter per channel) and lands a `draft` content item with a per-channel adaptation and a first `ai` version row for each, which is what provenance is later computed against. Every finished step is checkpointed in `pipeline_runs.steps` — `adapter:<channelId>` per channel, so a crash mid-fan-out does not re-buy the channels that succeeded — and a ledger row is written for every physical model call, in its own transaction, before the step's checkpoint, attributed to the step (and channel) that made it. The handler is fenced: a pg-boss heartbeat does not extend `expireInSeconds`, so an expired-but-live run gets re-dispatched, and without a fence both handlers would skip the same checkpoints, re-run the rest at the organization's expense, and both write a content item. The fence token is the job id plus a per-delivery nonce, because pg-boss reuses a job's id across retries: a later delivery takes the run over, the earlier one stops before its next model call, and the claim's `queued | running` guard is what makes a second draft impossible once one has been written. A permanent error records itself on the run and completes the job; only a transient one is retried, resuming from the last checkpoint. Cancelling, and having the brand deleted underneath the run, both stop it without an error — ledger rows already written are kept, because the money was spent. A channel deleted while a run is working costs that channel its adaptation and nothing more: the terminal write re-reads the channels under a lock instead of trusting the list the run started with, so the draft still lands for the ones that remain, and only losing every channel fails the run. The delivery also stops on pg-boss's own abort signal, which fires at the expiry that lets a second handler start — earlier notice than the fence can give.

- Generating a post from the web app: the compose screen grows a brief field with a **secondary** Generate action beside it — "Create post" stays the screen's one primary action — under the same preconditions Create post enforces (a brand, at least one channel). Generate does not fill the form; it discards the typed draft and starts a run that lands a different item minutes later, so a non-empty body is confirmed before it is thrown away, and with no AI key configured the action is absent entirely, replaced by a line linking to Settings. Starting a run opens a receipt at `/content/runs/[id]` showing the five steps as a live checklist and, on success, a **Draft ready link a human clicks** — never an automatic redirect, which would satisfy the publish gate's "a human read this" signal with no human involved. The queue lists open runs as strips above the cards, from `GET /api/runs?state=open`: failures sort first, stay until dismissed, and carry the run's error verbatim with Try again / Dismiss, because a failed run creates no content item and its strip is the only place the failure exists. A run leaving that list re-reads the content list, so the draft it produced appears without a reload. Run statuses reach the UI through a total `Record<RunStatus, StatusBadgeStatus>`, so a new status is a compile error rather than a sixth color. Posts now carry an origin badge — AI-drafted, AI-adapted (a human body with AI channel copy), or human-written — and the item screen stamps the read receipt (`POST /api/content/:id/opened`) once after render, through a new void variant of the API client, since a 204 has no body to parse.

- The AI layer these runs are built on (`packages/ai`): a model resolved from an already-decrypted org credential (Gemini or OpenRouter — the package has no database dependency and must not acquire one), structured output through `generateText({ output: Output.object })` with one repair attempt of our own, since that path has no `repairText` hook and does not retry a schema violation itself, a price table whose rates carry effective dates, and the five step definitions. Untrusted text — the typed brief, and every earlier step's output — reaches the model as nonce-fenced material in `prompt`, never in `instructions`, which is the prompt boundary the SDK's separate instructions field exists for. Metering hooks `executeLanguageModelCall` through a per-call telemetry integration, which the SDK invokes inside its own retry closure: every physical round trip becomes a ledger row, including the ones its retries made and the ones that failed after the provider had counted tokens.

- Generation runs over the API: `POST /api/runs` writes the run and enqueues its pg-boss job in one transaction, refusing a fourth concurrent run for an organization (409, under an advisory lock so the count cannot be stale) and a brand with no channels (400, because the run would otherwise land an item with zero adaptations that approval would happily mark approved while enqueueing nothing). `GET /api/runs?state=open` feeds the queue strips — `open` is deliberately not a status enum member, since it spans three statuses plus "nobody dismissed it". `POST /api/runs/:id/cancel` cancels the job and the run together (a status write alone would leave the job spending money to completion), and `POST /api/runs/:id/dismiss` clears a finished run off the strip without deleting the record of it.

- The publish promise, enforced in the API rather than the UI: approving an AI-drafted item is refused with 409 while nobody has opened it and nothing has been touched — the body and *every* adaptation still verbatim what the model wrote, compared under the same whitespace and Unicode normalisation the provenance mask uses, so a stray space or an NFD paste is not a human touch. Missing evidence refuses rather than passes. Each channel is judged against the version of the text it will actually send: clearing a per-channel override makes that channel fall back to the item body, so it is then compared with the item's AI version — clearing removes text without writing any, and is not a human touch. `POST /api/content/:id/opened` is what stamps the read receipt, once, and it is its own endpoint on purpose: a GET that stamped it would hand the future public API and MCP server the ability to open the gate by listing content.

- The provenance lens: an editor toggle that dims the sentences of a draft still verbatim what the model wrote, on the body and on every per-channel override, recomputing as you type. The surface is a real `<textarea>` with a mirrored overlay rather than an editor framework — the browser keeps caret, IME, dead keys, selection and undo, and no dependency is added — and the overlay renders from `splitSentenceSpans`, a **lossless** partition of the text where every character, separators included, belongs to exactly one span. (The old splitter trimmed its pieces and swallowed newlines, so an overlay built from it would have rendered a different character stream than the textarea and slid every highlight off the words it describes from the first line break onward.) `GET /api/content/:id` now returns `aiVersionBodies` — the `ai` version bodies for the item and each adaptation — and the mask is computed in the browser from the same `@pubrick/shared` functions the API uses, because a server-computed mask would still have to be aligned to a split done in the browser. Dimming reads **every** `ai` version through `aiSentenceMaskAny`, which ORs per-version masks instead of masking against them joined: `aiSentenceMask` consumes each AI sentence at most once on purpose, so a concatenated reference would dim a human's own duplicate of a sentence the model wrote once. Spans and flags are paired only by `dimSpans`, which knows that a blank span consumes no flag. The lens ships **off by default** (the badge already carries the claim at a glance; the lens is the detail view), and steps aside for IME composition, forced-colors mode and printing.
- The fourth origin badge: an AI-drafted item whose body matches no `ai` version now reads **human-edited**. Increment 1 shipped three of four only because the version text never left the server. The badge asks **any** `ai` row (`bodies.some(b => isUntouchedAi(body, b))`), which is deliberately not the publish gate's rule — the gate reads the *first* row, and the two coincide only while there is one row per level.
- The per-channel character counter tells the truth: its denominator is `min(platform limit, MAX_BODY_LENGTH)`, so an X channel reads `/ 280` and a Bluesky one `/ 300` instead of one `/ 4096` for every platform while the adapter generates against the real limit. That formula now lives once, in `@pubrick/shared`, and both the adapter and the counter read it; what each still decides for itself is the unknown-platform policy (the adapter refuses, since a wrong limit spends money on unusable text; the counter falls back, since it must not take the editor down over a denominator). The `maxLength` attribute deliberately does **not** drop with the denominator: an override already longer than the platform limit stays editable, or it would be unfixable forever. Over-limit text is shown as over-limit — the counter turns red — and saved as typed, never truncated; nothing on the write path enforces a per-platform bound, and the design records why that is the choice rather than a gap.

### Changed
- Migrations run under a Postgres advisory lock, so parallel test workers and multiple api replicas can no longer race each other on a fresh database.
- Documentation caught up with this increment. The pattern dossier's §5.1 (AI lives in selection + `⌘K`) is amended rather than quietly contradicted: it governs the refinement of existing text, and whole-draft generation from a brief is a compose-time input, so AI appears in three places now, two of them in the editor. `docs/specs/0001-product-design.md` §5's metering sentence is corrected — metering is a per-call telemetry integration on `executeLanguageModelCall`, not `wrapLanguageModel` middleware, which cannot say which step or channel a call belongs to when one model object serves the whole run. `CLAUDE.md` gains the generation rules worth enforcing on every future change: ledger rows commit before checkpoints, every model call runs under the run's fence, the publish promise stays server-side, the fact-checker verifies nothing until it has sources, and no test may call a provider.
- Compose has no fallback values for `BETTER_AUTH_SECRET` / `APP_ENCRYPTION_KEY` — an install without them fails immediately instead of shipping the repo's published key; the api port is bound to `127.0.0.1` (the web app proxies `/api`).
- `APP_ENCRYPTION_KEY` is validated at boot (base64 → exactly 32 bytes) rather than at first channel create.
- Channel form asks for each platform's real credential fields (all 8 platforms), masks secrets, and clears entered values when the platform changes.
- Organization slugs handle non-Latin names; onboarding stops on a failed `setActive`.
- API errors surfaced by the web app no longer leak raw Nest JSON; a 403 with no active organization sends the user to onboarding.
- Rejecting an approved item now actually cancels delivery: every queued or scheduled adaptation goes back to `pending` and its pg-boss job is cancelled in the same transaction, and the worker refuses to publish a job whose content item is rejected.
- A scheduled post can be rescheduled or published immediately: approving an already-scheduled item cancels the outstanding job and enqueues a fresh one at the new time instead of returning 200 and changing nothing.
- The publish queue contract (names, options, job payload) lives in `@pubrick/shared` and is imported by both the api and the worker, instead of being duplicated in each.
- The publish queue sets `heartbeatSeconds`, and its expiry is a bound on a whole attempt rather than a liveness check, so a live handler is no longer reclaimed and re-run (a duplicate post).
- The worker validates stored credentials against the adapter's schema before sending, so a malformed channel gives a named field error instead of an opaque platform 400.
- `PATCH /content/:id` rejects an empty body with 400 instead of 500, and `scheduledAt` must be in the future.
- Errors on the content screens distinguish what the operator can act on: a 4xx is shown as the server phrased it, while a 5xx or a failure with no HTTP status at all (network, proxy error page) becomes a translated "something went wrong" instead of raw English.
- A published link is rendered as a link only when it is `https://`; anything else is shown as inert plain text, since the URL comes from a platform adapter rather than from this app.
- The approve/reject buttons are disabled, with the reason spelled out, on an item that has already been published.

### Fixed
- The database now bounds publication bookkeeping: a partial unique index allows at most one `published` publication row per adaptation, and the worker checks for one before sending. This makes a re-delivered or re-approved job a no-op; it does not make a duplicate *post* impossible, since the send happens between that check and the record (a process killed in between leaves no record and a later attempt sends again).
- A late dead-letter delivery no longer clobbers a re-approved adaptation — `markExhausted` acts only on an adaptation still in `publishing`.
- Rejecting an item whose delivery is mid-attempt (`publishing`, e.g. part-way through a transient retry chain) no longer strands it: the adaptation goes back to `pending` and its job is cancelled, so it can be approved again.
- A publication that is already recorded no longer reports as a recording failure — the worker converges the adaptation's status instead of retrying a write that can only violate the unique index again.
- `getPublisher` no longer returns inherited `Object.prototype` members (`getPublisher("constructor")` was truthy but not a publisher).
- Approval now pins the content. Editing an item's body or a per-channel override after approval returned 200 while the adaptation kept its live job, and the worker reads the body at execution time — so unreviewed text was what actually published. Both edits are refused with 409 once the item leaves `draft`/`rejected`/`failed`, with a message naming the status the user is looking at rather than one sentence for every state.
- Approve and reject on an already-published item are refused with 409 instead of permanently storing `approved`/`rejected` over `published` — a status nothing repaired, since `recomputeItemStatus` only runs from the worker.
- Rejecting an adaptation clears its `lastError`, so a rejected row no longer shows the previous attempt's platform failure.
- `lockAdaptations` orders its `SELECT … FOR UPDATE` by id, so two concurrent approves of one multi-channel item cannot lock its rows in opposite orders and deadlock (a 500 on a merely duplicated request).
